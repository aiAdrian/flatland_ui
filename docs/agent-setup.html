Agent setup: tree search with learned node evaluation

A tree search over real network states; neural networks judge each state as it is, with nothing completed or planned ahead. Sections 1–7 are the design; §8 is what it replaced, §9 what is built today, §10 what comes next.

1  The shape of the thing

One tree search. Nodes are states of the railway, edges are joint decisions. Every node is scored by neural networks that look at the raw, unfinished state — no shortest-path completion, no baseline planner, no simulated look-ahead. The score decides which part of the tree to grow next. The search runs continuously alongside the live simulation and always has a current best answer.

2  What a node is

The root is the state at the moment the first train reaches a decision point. Departures and the run up to that point involve no choices, so they are not part of the tree.

A node holds the state of the whole railway at one instant. For the networks, that state is projected onto the decision-point graph: every train currently travelling between two nodes is drawn at the node it is heading for, together with the number of steps it still needs to get there. The projection is a representation device only — in the simulator the train really is mid-track and really has to finish those steps before it can decide anything.

3  What an action is

What a train may choose is decided by the geometry it is standing in, and the two kinds of choice never occur together. A train can only pick a direction where the track actually divides ahead of it, and it can only be held where holding it achieves something.

A wait holds the train for 1, 3, 5 or 10 steps and leaves it on the same node, which becomes a decision point again when the wait is over. Long holds are therefore built by waiting repeatedly, and a merge is re-evaluated after every hold against what the other trains did meanwhile. "Go" is simply wait 0: the train leaves.

Consequence worth knowing. A train approaching a split cannot be chosen to stop there. If the branch it takes is occupied, the simulator holds it anyway — it is just not a decision. Deliberate holding is expressed one node earlier, at the stop or merge the train came from.

The joint action

A branch of the tree is one joint action: the cross product of the option lists of every train standing at a decision point at that instant.

Expanding to the child state

Once a joint action is fixed, a fast graph-level simulator advances the world: trains move along decision-graph edges at their travel time, waits count down, cell occupancy is respected. It runs until the next train arrives at a decision point — that instant is the child node. No Flatland stepping, no environment copies; milliseconds per node.

The trade this makes. The fast simulator is a model of Flatland, not Flatland. It has to reproduce blocking, head-on deadlocks and arrival times faithfully enough that a plan good in the model is good in reality. That equivalence needs its own test suite — it is the single biggest correctness risk in the design.

4  Choosing what to expand next

All unexpanded nodes across the whole tree sit in one frontier, ordered by

priority(node) = V(node)  +  c / √( 1 + siblings already expanded )

The first term is the networks' verdict; the second is a small bonus for branches whose neighbourhood has barely been touched, so the search cannot collapse into a single line early on. Because every network output is a utility between 0 and 1, the constant c has the same meaning everywhere and is one tunable number. The bonus only ever shrinks, which is what lets a queued priority be trusted as an upper bound and re-ranked lazily when it is popped — no rescoring of the whole frontier.

The value of a node is the weighted sum of the metric networks' outputs, using the user's sliders — the same dials that already exist in Director mode. A node where all trains have arrived is terminal: its metrics are measured exactly, no network involved.

Why the search also has to dive. A node's value estimates the end it leads to, and that estimate does not shrink as the run progresses — so a half-finished state looks exactly as good as the best state below it, and pure best-first spreads sideways forever without ever finishing a run. Every so often, and always while no complete run is known yet, the search therefore follows its own preference straight down to the end. The dive does not evaluate anything: the states it passes are ordinary nodes, valued like any other, and only the terminal it reaches is measured. It is how solutions are found, not how they are judged.

5  What the networks predict

One network per metric. Each takes the node state described in §2 — nothing else, and in particular nothing completed or planned ahead — and outputs a single number in 0–1.

Crucially, that number is not "how good is this state right now". It is how good the final solution will be if the search continues from here, choosing high-value nodes as it always does. A half-empty state whose trains are all badly placed but from which the search reliably recovers should score high; a tidy-looking state that always ends in a deadlock should score low.

Start with one network — punctuality (all trains arrive, and total delay) — and get the whole loop working end to end. Connections and stability are added afterwards as identical copies with different labels; nothing in the search changes when they arrive, since the value is already a weighted sum.

6  Training

This is a self-play loop in the AlphaZero shape, with the simulator in the role of the opponent-free judge.

The three things that make this work

  1. Cold start. Generation 0 has untrained networks, so the search is effectively undirected — that is fine and expected. It still produces complete solutions (badly), those get measured, and generation 1 has something to learn from. Each generation's search is better, so each generation's labels are better.
  2. Exploration noise. If the search always follows its own preference, the data only ever covers states the current networks already like, and the loop stalls. Add noise at the root of each self-play search (AlphaZero uses Dirichlet noise on the root's action priors) and sample among the top options early in a run rather than always taking the best.
  3. A policy prior. The largest speed-up in AlphaZero-style systems is not the value network but a second head that predicts which action the search will end up preferring, trained on the search's own choice distribution. It orders children so the good ones are expanded first. Recommended as soon as the value loop works — it is what makes the branching cap in §3 cheap instead of arbitrary.

Practicalities

  • Labels are utilities in 0–1, so the same loss (binary cross-entropy on the logit) keeps every network's output in range by construction.
  • Keep a replay buffer of the last few generations rather than only the newest, and hold out whole scenarios — never individual states from a scenario also present in training — or the metrics will flatter themselves.
  • Data grows fast: one scenario yields one label per node on the executed path, and the path is dozens of nodes long.
  • Accept a new generation only if it beats the previous one on held-out scenarios by measured outcome, not by prediction error.

7  Running alongside the live simulation

The search is not a phase that ends. It runs in parallel with the running simulation and is queried at any moment for the best complete solution found so far.

When reality diverges — a breakdown, or a train not where the model said it would be — the affected subtree is invalid. The nodes whose states no longer match are dropped and the search continues from a freshly built root; whatever is still consistent is kept. The design must never assume the model and the world stayed in step.

8  What this replaced

The previous planner searched over half-written timetables and scored them by finishing each one with shortest paths first. It has been removed; this is what changed.

Removed: the completion-based search, the three plan-level networks and their trainers, the candidate-scoring ensemble, the dataset encoders, the curriculum and evaluation-set tooling, and the branch prior — fifteen modules. Kept and reused: the decision-point graph (now with split approaches as a third node kind), schedules and their player, stations, planned connections, the measured rollout, the static safety measure behind the verify endpoint, and the whole mid-episode capture / splice / rollout-gate machinery.

What it measures

  • Speed. ~2,500 expansions per second on the 7-train stress preset (30×30); the default planning budget of 600 expansions takes about a quarter of a second and builds a tree of ~1,900 nodes, 33 levels deep.
  • Correctness against Flatland. Plans the model approves are replayed in the real environment and match: same arrivals, same total delay, within one step on episode length. On the stress preset the search gets 7/7 trains home with zero delay, verified by replay — where the reactive policies strand three to seven of them.
  • Value of searching. On networks tight enough that driving straight at the problem deadlocks, the search finds the holds that get the trains through — that is a test, not an anecdote. On roomy networks it matches the obvious policy, which is the floor it must not fall below.

What is not finished

  • The value network does not yet earn its place. It learns to predict outcomes (R² ≈ 0.5 held out, at the small scale trained so far), but a search guided by it scores worse than the unguided one — around 0.20 against 0.42 on held-out scenarios — so the acceptance gate has rejected every generation. This is the expected shape of an early AlphaZero loop: one label per state, shared across a whole run, needs far more games than have been played. The gate is doing its job — a network that does not help cannot reach the app.
  • The search does not run continuously. It plans on demand and on events, keeping and re-rooting its tree, but nothing grows it between environment steps while an episode runs.
  • No value-based pruning. Branches end naturally at terminal states, and the node cap releases the worst unexpanded leaves, but the "hopelessly below the best solution" cut described in §7 is not implemented — deliberately, since its failure mode is silent.
  • Breakdowns are not modelled during search. A malfunction in progress is read as a hold of that length; the search then plans a disturbance-free world and relies on re-rooting when the next one happens.

10  Next steps

In the order that makes each one worth doing:

  1. Train at scale, and find out whether the value network can beat the unguided search. Thousands of scenarios rather than dozens, more generations, and a wider mix of network sizes. The whole loop and its gate already run unattended — this is compute, not code. If several serious attempts still lose to the unguided search, that is a real finding about the labelling scheme, and step 2 is the answer to it.
  2. Add the policy prior head (§6). Predicting which option the search will end up preferring is the biggest known speed-up in AlphaZero-style systems, and it addresses this loop's specific weakness: every state of a run currently carries the same label, so the value head learns slowly, while the prior learns from every decision. It also turns the child cap from a blunt rule into a ranked one.
  3. Run the search continuously (§7). Grow the tree on a background thread between environment steps, re-rooting as decisions execute, so the plan improves while the episode runs instead of only at planning moments. The pieces — re-rooting, the node cap, the live-state read — are in place; what is missing is the thread and the locking around the tree.
  4. Add the second and third metrics. Connections and stability need a definition measured from the simulator (§5), one network each, and nothing else: the search already combines a weighted sum, and the dials already report themselves as inactive until then.
  5. Tune what is currently guessed: the exploration constant, the child cap, the dive interval, and the planning budget — against measured outcomes on a fixed scenario set, not by eye.

Two things to watch while doing any of it. The fast simulator is a model of Flatland, and every widening of the scenario mix is a fresh chance for the two to disagree — the replay comparison is the test that catches it. And the search currently has no way to know it is about to strand a train that the naive ordering would have saved: the floor test in the suite is what keeps that honest.
